## What this phase shipped

Section A synthesizer upgraded from pricing-only to **multi-collector**. The synthesizer now reads from BOTH `pricing_packaging` AND `tech_stack` and produces cross-signal narrative. First multi-collector synthesizer call in the project.

- **Synthesizer body** at `rrxray/synthesizers/observed_gtm_motion.py` reads both collector outputs from `ctx.collector_outputs`, skips synthesis only when ALL collectors are absent (graceful partial-failure handling). Future widenings (`revenue_motion` in 2.1c, `content_demand` in 2.1d, etc.) drop in as additional conditional blocks without restructure.
- **File renames** (via `git mv` for clean history): `_pricing` suffix dropped from synthesizer module + prompt template + test file. Pipeline import updated.
- **Tests:** 5 new tests added (4 multi-collector synthesizer tests + 1 pipeline regression test). 14 total synthesizer tests now passing.
- **Live smoke runs** against three domains (Swayable, SQA Services, Linear) all produced multi-signal Section A narratives with cross-signal reasoning — Linear in particular captured specific tier prices and identified the "PLG architecture but no client-side product analytics" gap as a real diagnostic finding.

## Quality gate — what surfaced and what was approved

The quality gate ran one full pass against three domains (Swayable, SQA Services, Linear). The synthesizer was approved on the first pass — no prompt iterations were needed. Specifically:

- **Linear** demonstrated the cross-signal reasoning working as intended. The narrative captured specific tier prices ($0 Free, $10 Basic, $16 Business), read the Free tier's soft ceilings (2 teams, 250 issues) as deliberate expansion design, and surfaced "PLG architecture but no client-side product analytics" as a real diagnostic finding. Mentioned Triage Intelligence + Linear Agent as Business-tier features mapping to upmarket arc.
- **Swayable** picked up the low-confidence HubSpot DOM-anchor + gated pricing combination. Framed the GTM Gap™ honestly as "enterprise commercial intent + minimal observable martech" with three plausible explanations (early-stage, server-side, lean build).
- **SQA Services** correctly read the absence of detectable signals as itself diagnostic — services-firm motion likely running through referrals + offline channels, no formal demand-gen infrastructure.

The cross-signal reasoning works. Each Section A integrates pricing + tech_stack rather than just listing them in series. Voice post-processor caught the trademark insertion (`GTM Gap™`) on each run; no forbidden-word violations surfaced.

## Known issues / limitations

The Phase 2.1a tech_stack-collector limitations carry forward unchanged:

- **Firecrawl strips `<script>` tags** even with `only_main_content=False`. The DOM-level loose signatures from Phase 2.1a-fix help (Swayable's HubSpot was caught via the `hs-web-interactives` anchor) but tech_stack data on most domains is still sparse. The new synthesizer prompt handles this gracefully — the "Tech Stack signal" block renders the absence as itself a signal, and the synthesizer reasons about whether absence reflects privacy posture, server-side tagging, or low maturity. This is the right framing.
- **Linear smoke had zero tech_stack detections** despite Linear obviously running product-analytics tooling. This is the same Firecrawl limitation. Expand the catalog further when more tools surface as DOM-only fingerprints.

Other Phase 1 known limitations also carry forward (cache thundering-herd, voice log entries from failed synthesizer persisting in flush, templates packaging for wheel installs, archive.org transient outages).

## Process notes

**Workflow used:** Subagent-driven-development with TDD. 5 tasks total, dispatched in sequence. Skipped formal spec-review and code-quality-review on T1 (mechanical rename) and T4 (regression test) — implementer's TDD self-test plus my local verification was sufficient signal. Did full implementer dispatch on T2-T3 (the actual logic changes).

**What worked:**

- Smaller cycle (5 tasks vs Phase 2.1a's 8) ran faster: ~1 hour of subagent execution vs Phase 2.1a's ~1.5 hours.
- Generic "available signals" prompt frame paid off immediately. Each conditional block stands on its own; no template restructure needed when the next collector lands.
- Voice-post-processing-on-every-string discipline (paragraphs, bullets, findings.text, gaps, questions) is now a settled pattern. Future synthesizers just copy it.
- Live quality gate against THREE domains caught zero issues — the prompt was right on first try. This is partly luck (the framework guidance was thorough) and partly the architecture (the prompt template inherits Phase 1's tight system-prompt voice rules).
- "git mv" for renames preserved blame history cleanly. R100 / R97 / R88 ratios in `git log --diff-filter=R`.

**What surfaced:**

- The implementer caught a fourth file (`tests/test_prompts.py`) that referenced the old prompt name and updated it. This wasn't in the plan's file list. Lesson: when renaming files, grep the whole repo for the old name before declaring done, not just the obvious consumers.
- Token budget: this session has now executed Phase 1, Phase 2.1a, Phase 2.1a-fix, Phase 2.1b end-to-end. ~50+ commits total across all phases. Significant token consumption. The next phase (2.1c) should expect either a fresh session or a cache-warmed continuation.

**Pacing:**

- Phase 1: 6 hours, 36 commits, 23 tasks
- Phase 2.1a: 1.5 hours, 9 commits, 8 tasks
- Phase 2.1a-fix: 0.3 hours, 1 commit, narrow scope
- Phase 2.1b: 1 hour, 6 commits (4 implementation + spec + plan), 5 tasks

Phase cadence is converging on ~1-1.5 hours per sub-phase as the architecture stabilizes. Phase 2.1c should land in similar time.
