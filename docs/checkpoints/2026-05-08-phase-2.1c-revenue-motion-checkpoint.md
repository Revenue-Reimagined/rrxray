**Process improvements that landed in this branch (post-execution but pre-merge):**

## Known issues / limitations

- **Linear's role categorization put all 42 open roles in `other`.** Likely correct — the catalog only has GTM-role keywords by design, and Linear is a PLG-heavy company likely hiring engineers + designers + PMs. The synthesizer interpreted this as "no GTM hiring," which reads diagnostic. Worth a spot-check on a future session: pull a few of Linear's actual job titles from the careers page raw and confirm none of them should have hit the catalog. Deferred to whenever someone has time; not a blocker.
- **Wayback 503s during Swayable re-run.** Known env behavior (CLAUDE.md notes archive.org returns 503s under load). Has retry-with-backoff. Graceful degradation handles it. Not a defect.
- **LinkedIn search via Firecrawl is best-effort.** Some queries return zero results even for active companies. Synthesizer frames absence as a signal, not a failure. Phase 2.1c-fix could add Bing-search fallback if needed; not currently needed.
- **Two trademark substitutions per Swayable run** — `GTM Gap` → `GTM Gap™` was applied twice (paragraphs 0 and 2 both contained it without TM). The voice processor's trademark sub uses `count=1` per call, but `_voice` is called once per paragraph, so each paragraph gets its own first-mention substitution. This is the intended behavior; both end up with TM in the rendered output. Worth noting for clarity, not a defect.

## Process notes

**What worked:**

- Two-stage review (spec compliance + code quality) was selectively applied: skipped on truly mechanical tasks (T2 schemas, T3 field addition, T4 catalog, T12 pipeline registration) and run fully on logic tasks (T5-T11). Per-task judgment was correct in retrospect.
- Phase 2.1c execution ran on Sonnet 4.6 implementers + Haiku 4.5 reviewers. The new model matrix calls for Opus on real-logic implementers going forward; Phase 2.1d / 2.2 will be the first phases to run under the upgraded matrix.
- Quality-gate iteration cycle worked exactly the way Phase 2.1b documented it: first run surfaced a real voice issue, fix went in (prompt tightening + sanitizer extension), re-run confirmed clean. One iteration, ~15 minutes.

**What surprised:**

- The voice violation was a forbidden word rather than an em-dash; em-dashes have been the recurring failure mode through Phase 2.1b. The fix pattern (substitute, don't raise) is the same — sanitizer table just needed extending. Now both classes are handled the same way.
- The CLI dry-run staleness had been silently broken since Phase 2.1a; nobody noticed because the live runs work regardless. Worth a periodic audit of "does what we tell the user match what the code actually does" — display surfaces drift from logic surfaces.

**Token-budget observations:**

- Most of the implementer subagent budget went to T5-T9 (collector logic). Reviewer budget was minimal because Haiku handled it cheaply.
- The Dale-led quality gate iteration was the most expensive controller phase per minute (Opus + multiple back-and-forth + tooling) but the cheapest in terms of total spend ($0.24 for 4 live smokes).

**Recommendation for Phase 2.1d / 2.2:**

- Use the model matrix from day one. The cost difference between "Opus controller talking to Sonnet implementers" and "Opus controller talking to Opus implementers" is measurable but worth it on logic-heavy tasks per Dale's explicit ask.
- When the first quality-gate run hits a voice issue (highly likely — it's been the pattern in every phase), the fix is now templated: extend the sanitizer table OR tighten the prompt OR both. Don't try to extend the LLM's self-discipline beyond what's been working.
- Two parallel Coders is novel for this project. Watch for `CLAUDE.md` / `roadmap.md` / `pipeline.py` conflicts. Encourage both to commit briefly with focused diffs so rebases stay easy.
